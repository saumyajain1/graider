# Submission tables and rubric grading

This follow-up addresses the six requested corrections. The additional changes for findings 12, 13, 14, 16, 18, and 23 are documented below. Findings 15, 17, 19–22 remain deferred.

1. **Submission/review queues:** replace per-student cards with a shared table. Search by name or student number and combine that search with a status filter. Show grades, status, intake source, submission date, and Review actions; student responses and detailed errors belong on the full review page. The submission table retains individual AI grading actions.
2. **Grading inputs:** the existing pipeline already supplied the saved reference answer and every rubric description/maximum. Tests now verify those inputs reach the provider prompt. Each criterion also has an explicit ID so returned scores can be matched to the correct rubric entry.
3. **Criterion grades and manual review:** AI returns one score and feedback for every rubric criterion. Validate exact criterion coverage, uniqueness, score bounds, and two-decimal precision before saving. Store rubric titles, descriptions, maximums, and separate AI/teacher scores and feedback as a result snapshot. Calculate question totals from criterion scores and assignment totals from question totals. Ungraded submissions show blank editors and their full response, allowing manual grading without an AI call. Blank criterion scores remain ungraded; partial work can be saved without inventing a completed total. Preserve teacher criterion overrides during regrading. Earlier aggregate-only results retain their original grades and explain that a breakdown requires regrading or manual criterion entry.
4. **Overview:** remove the redundant dark “Set up your questions” card.
5. **Overview layout/navigation:** place assignment text below the replacement-file control and put Save and continue next to Back at the bottom. Saving drafts before navigation remains intact.
6. **Questions:** remove the extra Back link from the generation card and use “Workflow step,” matching reference answers and rubrics.
7. **Dashboard:** remove the extra Edit questions shortcut from assignment cards.
8. **Review errors:** validate review responses before rendering. The local preview was still running an older backend that omitted the questions and rubric breakdown expected by the rebuilt frontend. Restart that preview with the current backend and preserve its existing database. Incompatible responses now show a retryable review error; unexpected rendering errors show a safe page fallback with Refresh and Back actions inside the workspace.

## Follow-up findings 12, 13, 14, 16, 18, and 23

- **12. Unsaved work:** share the draft registry across the workspace. Sidebar, Back, profile navigation, Google connection, and sign-out offer Save and leave, Discard and leave, or Stay. Validate edited drafts before starting writes, preserve remaining drafts if a save fails, and keep the user on the page on failure. Refresh, tab closure, and other full-page navigation use the browser's unsaved-work warning. Drafts are kept in page memory; browser-restart recovery remains a separate decision.
- **13. Finalization:** Save and finalize saves edited review fields before requesting finalization. The server locks the submission and checks question coverage, valid score bounds/totals, complete criterion scores, and cleared review flags before changing its status/timestamp. Editing or regrading a finalized review clears its completion timestamp. Partial grades may be saved but cannot be finalized. Validation failure never marks a submission finalized.
- **14. Replacement uploads:** explicitly choose text extracted from the replacement file or the edited assignment text. Preview extraction before accepting the new file's text; failed extraction leaves the stored source untouched. A teacher-scoped preview API checks file type, upload size, PDF page count, and extracted-text length without storing the upload. The update API honors the explicit choice even when the previous text is included in the request. Regenerating questions remains a separate deliberate action.
- **16. AI replacement:** default generation fills missing answers/rubrics. Save valid edited drafts first so missing-only generation preserves them. Individual replacement and Replace all ask for confirmation that includes unsaved edits; cancellation keeps the content. Prepare all answers/rubrics before replacing them in one database transaction, so provider failure leaves earlier content intact. Recheck missing items after the provider returns to preserve teacher content added during generation. Keep loading states scoped to the selected action.
- **18. Account management:** add Forgot password, one-hour single-use recovery links, password confirmation/validation, editable names, and password changes requiring the current password. Changing a password keeps the current session while invalidating other sessions; email recovery invalidates sessions and requires a new sign-in. Google disconnection requires a password and its confirmation. Google-only users can establish a password through their mailbox first. Recovery requests return the same message for existing/missing accounts and are rate limited; provider errors and reset tokens are not exposed in API responses. Use HTTPS email delivery through Brevo on Render; development without a key prints emails locally. [ACCOUNT_SETUP.md](ACCOUNT_SETUP.md) covers configuration when email recovery is enabled.
- **23. Readiness:** derive workflow badges from valid scored questions, nonempty reference answers, and positive rubric allocations that exactly match the question total. Incomplete setup takes priority over submission/review statuses. Rubric/question edits refresh assignment caches so dashboard badges reflect the saved state immediately.

These changes require no database migration or reset. They are implemented on `feat/production-deployment` but are not deployed. PR #2 remains unmerged. The owner chose to defer email-provider setup; password recovery remains disabled in production until it is configured. No real emails were sent during verification.

## Google sign-in on the admin login page

Django's built-in admin login was password-only, which prevented a Google-only administrator from signing in directly there. Add a Graider admin login template with the multicolor Google symbol, retaining the password form. A CSRF-protected POST starts the existing nonce/PKCE Google flow and returns to the requested admin page. It shares the Google authentication rate limit and ignores external redirect destinations. Only an active, existing staff account with Google already linked can sign in this way; the admin flow never registers, links by email, or promotes an account. Cancellation/provider errors return a safe message on the admin login page. Servers without Google credentials show that Google sign-in is unavailable.

Validation: all 181 PostgreSQL backend tests passed, including eight new admin-login regressions. Repository lint/format, generated OpenAPI validation and migration consistency passed. A real Google sign-in with the owner's authorized account reached the admin dashboard successfully on `http://localhost:5173/admin/`. That localhost callback was already registered; the `127.0.0.1:18007` callback was rejected by Google and was not added to the client.

The original UX preview on port 18009 uses a separate SQLite database without Google configured; it cannot authenticate the live Google identity. The configured local app on ports 18007/5173 uses the Neon `admin-google-login` branch created from production (`br-little-art-b5q87k65`). The previously pending `grading/0002_criterion_results.py` migration was applied only to that copy, preserving the existing Google/staff account. Its runtime configuration is stored privately outside the repository; the committed/ignored dotenv files were not changed. Production database schema/data and deployed service are unchanged. AI calls and object storage are disabled in this local admin preview so it cannot spend tokens or modify production uploads. The preview branch is retained while this local app is in use. The port-18009 database was preserved when its backend restarted. This admin-login fix adds no migration and is not deployed.
